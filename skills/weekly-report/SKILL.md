# 运维项目周报生成

日报记录 `records/worklog/`，周报从该目录按配置窗口聚合。环境相关部分（文件名标题、模版、
固定第 1 条、业务线）在环境包 `config/weekly-report.yaml` 的 `report` 段声明；环境包
`skills/weekly-report/` 下的同名文件（本文件、`references/STYLE_GUIDE.md`）优先于这里的通用版。

## 核心规则

| 规则 | 说明 |
|------|------|
| **固定第 1 条** | 环境声明了 `report.fixed_first_item` 时，第 1 条使用该文本一字不改；未声明则无固定条 |
| **条数** | 本周工作总结 7-10 条（最少 6 条，除非日报确实没有内容）；下周待办 2-3 条 |
| **第三部分** | 标题固定为「三、下周待办」，写明确、可执行的 2-3 项下周计划 |
| **语言** | 面向客户运维汇报，不堆技术参数，说做了什么 + 为什么 + 效果 |
| **数据来源** | `records/worklog/` 下指定周期内的 `YYYY-MM-DD.md` 文件 |
| **屏蔽条目** | 带有 `- **周报**: 忽略` 的条目完全排除，不用于工作总结或下周待办 |
| **模版** | 环境包 `report.template`（缺省 `skills/weekly-report/assets/template.docx`） |
| **时间范围** | 以 `config/weekly-report.yaml` 的 `start_day` / `end_day` 为准；默认上周四 00:00 至本周三 23:59 |
| **输出** | `records/weekly-reports/<report.title><start>至<end>.docx` |

## 周报语言风格

详细示例见 [STYLE_GUIDE.md](references/STYLE_GUIDE.md)。

### 核心：面向客户汇报，非技术人员阅读

**好风格特征：**
- 每条从动词开头（完成/推进/针对/实施/开发/修复/持续/启动）
- 说清三要素：做了什么 → 怎么做的 → 效果/意义
- 多要点用分号分隔，不堆技术参数
- 用"显著/有效/持续/初步/进一步"等副词传递进展

**避免（仅限以下内部细节）：**
- 版本号（v2.0, v5.1）
- 行数/文件数/文件大小（910行, 1046表, 25KB）
- 脚本文件名（sync_check.sh, fix_schema_v2.py）
- 纯动作描述（只说了"做了什么"，无意义/成效说明）

**允许（组件名/平台名/关键参数保留）：**
- 具体服务和组件：HDFS, YARN, Hive, Spark, MySQL, Kafka, Prometheus 等
- 内部平台名：Grafana 等监控与管理平台
- 有意义的参数值：threshold=0.2偏低, 成功率70.2% 等

### 日报 → 周报改写示例

| 日报（技术纪要） | 周报（客户汇报） |
|---|---|
| 修复校验脚本：列名前缀 + DECIMAL精度 + 别名丢失 | 优化数据校验流程，修复列名匹配、数值精度对比及字段别名识别三项缺陷，有效降低校验误报率 |
| 开发同步任务监控脚本v2.0 910行 | 完成数据同步任务实时监控功能开发，支持导入异常的即时告警推送与任务状态追踪，并将监控部署为常驻服务 |
| 调大 NodeManager 堆内存并滚动重启 3 台 | 针对 NodeManager 内存告警实施 JVM 调优并分批滚动生效，告警明显收敛，未影响在跑任务 |

**关键：去掉版本号/行数/文件名，保留组件名和关键参数。**

## 工作流程

### 中台执行形态：四阶段 LLM 工作流

中台生成周报时必须连续执行以下四个 LLM 阶段，四个阶段都以本 `SKILL.md` 和
`references/STYLE_GUIDE.md` 为规则真源。代码只负责收集证据、传递结构化 JSON、
校验来源 ID 和写入 DOCX，不得用字符串模板代替 LLM 生成周报正文。

1. **事实聚合**：读取有效 worklog 的完整正文、结构化字段及其关联排查报告，为每条
   日志分配稳定来源 ID；发现跨日期、同组件、同问题和前后承接关系，按业务线形成主题组，
   并核对上一期周报待办的闭环状态。
2. **初稿**：只基于事实聚合结果生成客户口径初稿；相关日志合并表达，同一主题最多写
   1-2 条，不得退回“一条 worklog 对应一条周报”的流水账写法；每条正文保留来源映射。
3. **规则审查**：用原始证据反查初稿，逐条检查事实越界、遗漏、重复、业务线聚合、语言、
   禁止细节、条数、长度和待办验收点；输出问题清单与明确的改写指令，不直接写最终稿。
4. **二次改写**：结合原始证据、聚合结果、初稿和审查意见生成最终正文，修复所有事实与
   风格问题。最终总结和待办必须由 LLM 完成，代码不得为满足条数机械补句。

任一阶段都不得读取或推断带有 `- **周报**: 忽略` 的条目。事实聚合和最终正文引用的
来源 ID 必须能够回溯到本周期有效日志或上一期明确待办。

### 步骤 1：读取日报数据

从 `records/worklog/` 读取调用方指定的完整周报周期内所有 `YYYY-MM-DD.md` 文件；周期必须
符合 `config/weekly-report.yaml` 的开始日/结束日配置（缺省为周四至下周三）。提取所有 `[DONE]` 标记的条目
（可能有 `[WIP]` 条目用作待完成参考）。在状态筛选和内容归纳之前，先排除所有
带有 `- **周报**: 忽略` 元数据的条目；不得引用、改写或据此推断待办。

### 步骤 2：生成本周工作总结

按以下优先级排列条目：
1. 第 1 条：固定条（环境声明了 `report.fixed_first_item` 时）
2. 后续条目：按**业务线**聚合（业务线取 `report.business_lines`）→ 同一业务线内按重要性排列

**聚合原则**：同一业务线的多个日报条目应合并为 1-2 条周报条目，而非逐条列出。

**生成原则**：
- 固定条直接使用配置文本
- 每条约 40-80 字中文，必要时可用分号扩展
- 用完整的自然语言句子，而非 bullet points
- 确保 7-10 条（含固定条），最少 6 条

### 稀疏周期扩写

当周期内有效 `[DONE]` 日志少于 3 条时，仍按“最少 6 条”输出总结，但只能对已有日志做事实性拆解，不得虚构新的任务、指标或成果。可从同一条日志的标题、产出和过程步骤分别展开为：问题/目标分析、证据核验、结论沉淀、后续治理边界或能力建设等独立表述；同一事实不得重复改写。若日志确实没有任何有效内容，则只保留固定条目（如有），并在确认稿中说明本周期无可归纳工作。

### 步骤 3：生成下周待办

从日报 `[WIP]` 条目、[DONE] 条目里明确标注的「待办 / 未实施 / 未坐实」项，
以及上一期周报未闭环的待办中推断：

- **2-3 条**，宁少勿凑
- 每条简短，约 20-40 字，一行写完
- 格式：**动词开头的具体动作 + 预期目标/收益**
- **必须明确**：说清做哪件事、对哪个对象、达成什么效果，能被下周复盘时逐条对照验收
- 避免"继续跟进 / 持续观察 / 优化性能"这类无验收点的空泛表述

| 反例（空泛） | 正例（明确） |
|---|---|
| 继续跟进调度任务优化 | 推进核心视图补充分区键改造，使下游任务具备分区裁剪能力 |
| 持续观察集群内存情况 | 恢复 node4 节点日志采集服务，消除任务失败告警盲区 |
| 优化慢 SQL | 与业务侧确认两条流程的调度错峰方案并实施，消除并发覆盖引发的间歇失败 |

### 步骤 4：检查与输出

- 确认工作总结 7-10 条（最少 6）、下周待办 2-3 条
- 逐条检查语言：去掉版本号/行数/文件名/文件大小，但保留组件名和关键参数值
- 下周待办逐条自检：是否有明确对象与验收点，空泛条目重写或删除
- 每条应提及具体的服务/组件/工具名，避免过于笼统
- 确保没有超出日报覆盖范围的内容
- 稀疏周期扩写后的每条总结都能回溯到对应日志字段，避免为了凑条数添加未经记录的工作
- 用编号列表输出确认稿供用户审阅
- **无须用户确认**，写入 docx

## docx 操作（无须用户确认）

1. 解包模版 docx 到临时目录
2. 编辑 `word/document.xml`：
   - 修改时间文本为 "YYYY年MM月DD日至YYYY年MM月DD日"
   - 替换"二、本周工作总结"下的编号段落（numId=2）
   - 替换"三、下周待办"下的段落
   - 待办条目与工作总结一样使用**编号列表**：模版已配好 `numId=3`（引用与工作总结相同的
     abstractNum，附 `startOverride=1`，故编号从 1 重新起编）；
     新增条目时复制模版中已带 `<w:numPr>` 的待办段落，只换文本，勿手写"1."前缀
3. 打包到 `records/weekly-reports/<report.title>{开始日期}至{结束日期}.docx`
4. 清理临时目录
